## The problem and who it's for

myTrellis is a multi-tenant invoicing SaaS for sole traders and small businesses.

{/* TODO: 1 sentence on the specific problem it solves for them. What is wrong with the tools they use today? */}

It is built like enterprise software (tenant isolation, audit trails, tested restores, controlled releases) because small businesses still deserve their financial data to be treated carefully.

## What I built

Two products on one platform:

- **Customer app**: where each business manages clients, quotes, invoices, recurring invoices, expenses and reporting, and gets paid online with a pay link and QR code.
- **Admin app**: internal tooling for operating the product and supporting customers.

Around them sit a monitoring job, a shared design system (Roots) with platform-neutral design tokens, and an early mobile app.

## Architecture

Shared application servers, one PostgreSQL database per customer, and a small shared service that keeps track of which customer is which. Every request is scoped to a single customer before any data is touched.

### Typed end to end

Schemas are shared between the back end and the front ends, and the front ends consume generated, typed API clients. A change to an API surfaces as a compile error in the apps rather than a bug in production, and both APIs respond in one consistent shape.

### Design system

Roots is a Storybook-documented package: shadcn primitives as foundations, compound components (forms, data, tags, status, media, navigation) on top, and a tokens package that generates both the web CSS and a mobile theme so every surface shares the same visual language.

## Decisions worth explaining

{/* TODO: confirm each "why" below matches your actual reasoning; drafted from the repo docs, not from you */}

- **Database per customer, provisioned automatically.** Stronger isolation than row-level tenancy, and simple per-customer backup, restore and deletion. The cost is operational: every schema change has to reach every database (see Challenges).
- **Stripe Connect.** Each business keeps its own Stripe account and compliance relationship, funds go straight to them, and card details are handled by Stripe, never by myTrellis. That keeps the product a thin integration rather than a payments company.
- **Per-customer feature toggles, with who/when change tracking.** Features can be turned on for individual customers, and every change records who made it and when, so behaviour differences between customers can be explained.
- **Frozen snapshots on documents.** An invoice keeps the client and business details as they were when it was created, so editing an address later never rewrites history.
- **CSV import with validation preview and rollback.** Users see what will change before data is committed and can undo an import.
- **Scheduled automation for reminders and recurring invoices.** Overdue invoices and expiring quotes are handled by scheduled jobs rather than relying on users to remember.

## Challenges

### Schema changes across many databases

With one database per customer, "run the migration" is not one operation. A change is only live once it has reached every customer's database, and the release has to fail safely if any of them does not. I designed around the usual traps: changes follow an expand-and-contract pattern so old and new code can briefly coexist, and risky changes are split into small, reversible steps.

### Payments in an isolated-data world

External payment events do not know about our customer boundaries. Mapping them back to the right customer without weakening isolation meant treating every inbound event as untrusted until verified, making processing safe to repeat, and reconciling anything that was missed.

{/* <BaseImage src="projects/trellis/invoice-pay" alt="Invoice with pay link and QR code" caption="Each invoice has a pay link and QR code, settled through the business's own Stripe account." /> */}

### Provisioning that fails safely

Creating a customer means creating and preparing a database, which can fail halfway. Provisioning has explicit failure states, automatic retries and alerting, so a bad signup is visible and recoverable instead of silent.

### Recovering one customer

Whole-platform recovery tools cannot restore a single customer without touching the others. Per-customer backups, restored into an isolated environment first and reviewed before anything goes live, make recovery precise and low risk.

## Delivery

CI/CD runs on GitHub Actions to Google Cloud, with infrastructure defined as code in Terraform.

- **Automated gates.** Every change runs through automated tests before it can be released.
- **Deploy is not release.** Production changes are deployed, health-checked and then deliberately promoted by a person.
- **Safe by default.** Backups are required before risky changes.

## Quality and observability

- **Tests**: unit and integration tests, interaction tests for the design system, and end-to-end and visual regression tests, with a coverage floor enforced in CI.
- **Observability**: distributed tracing and error monitoring across the apps and APIs.
- **Monitoring job**: a scheduled job that checks platform health and alerts the team.

## Public site and documentation

Alongside the product sits a second monorepo for everything public-facing. Two Next.js apps share a small UI package and a single source of truth for URLs.

- **[mytrellis.io](https://mytrellis.io)**: the marketing site. Today it is a deliberate holding page (logo, light and dark theme, a link to the docs) while the product is in alpha. {/* TODO: update when the real marketing site ships, or drop this bullet if you would rather not mention the holding page. */}
- **[docs.mytrellis.io](https://docs.mytrellis.io)**: the product documentation, built with Fumadocs. It is written as a step-by-step alpha user guide for non-technical testers: getting started, core tasks (clients, quotes, invoices, line items, expenses), getting paid (online payments, reminders, recording payments), importing data from CSV, and going further (reports, recurring invoices, branding).

A few details I'm happy with:

- **Screenshots as a component.** Each guide embeds one component that shows a desktop and a phone capture side by side with click-to-zoom. Captures are converted to WebP by a script, so pages stay light without anyone thinking about it.
- **Task-shaped content.** Every page starts from something a business owner is trying to do, not from a feature name. Search keywords and icons are set per page, and the CSV import guides include downloadable template cards.
- **Same engineering standards as the product.** Conventional Commits enforced by commitlint and husky, linting and formatting in CI, a coverage floor, and Storybook for the shared UI package.
